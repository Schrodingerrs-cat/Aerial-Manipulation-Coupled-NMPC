Aerial Manipulation with Coupled NMPC

A drone with a robot arm that touches walls — how the controller works, why it is built this way, and what has actually been proven.

RBE 595-F07 · Optimal Control & RL Sahil Gajera · Aryan Shah Status: mid-project 30 Oct 2026

This document explains the project from zero. It assumes you know basic control and linear algebra but nothing about drones, manipulators or this codebase. Every claim points at the file that backs it.

Read this first

The project is not finished. The coupling comparison is done and strong; the part the proposal was actually about — comparing classical and learned model correction — is incomplete. Section 15 says exactly what is missing. Nothing here should be read as a final result.

Section 1The problem we are solving

Tanks, pipelines, chimneys and bridges have to be inspected for corrosion and cracks. Many of those inspections need a sensor physically pressed against the structure — an ultrasonic probe held flat on a steel wall, for example. Today that means scaffolding or workers on ropes: slow, expensive and dangerous.

A drone carrying a small arm could do it instead. The hard part is not flying. It is that the drone and the arm fight each other:

  • When the arm moves, the system's centre of mass shifts, so thrust that used to balance the vehicle now also twists it.
  • When the tool touches the wall, the contact force pushes back into the airframe.
  • A quadrotor cannot push sideways without tilting, because its four rotors only produce thrust along one body axis.

So the vehicle has to tilt to press, and tilting changes where the arm is pointing, which changes the contact force, which disturbs the vehicle. That loop is the whole engineering problem.

Section 2The research question

Nonlinear Model Predictive Control (NMPC) is a natural fit: it plans several steps ahead, handles the drone–arm coupling directly, and respects thrust and tilt limits. But NMPC is only as good as the model inside it, and the real model is always wrong somewhere — payload mass is off, contact stiffness is unknown, friction is unmodelled.

A popular fix is to bolt on a learned (reinforcement-learning) correction. But classical tools — a disturbance observer, an extended Kalman filter — have fixed model error for decades. So the proposal asks a sharper question than "does RL help":

The question

Which kinds of model error actually need learning, and which are already handled by classical methods?

The hypothesis is that it depends on the kind of error. A disturbance observer is reactive — it can only correct an error after it has shown up in the measurements. A learned policy can see the tool approaching the wall and prepare for the impact before it happens. So:

Parametric (arm mass, inertia)Non-parametric (contact, friction)
Slowclassical should be enoughclassical probably enough
Fast / suddenclassical mostly OKlearning should help

If learning does not win in some of these cells, that is still a publishable result. The project is designed so that a negative answer is an acceptable outcome, which is why the evaluation discipline in Section 12 matters so much.

Section 3The scope change — read this or you will be confused

Critical

The file proposal.pdf in this repository describes an older version of the task. The authoritative specification is Plan.md (25 Oct 2026). If you read only the proposal you will look for features that no longer exist.

Original proposalCurrent task (Plan.md)
A long probe on the armNo probe. Contact is a 12 mm rubber pad on the hand itself
Probe must stay perpendicular to the wallNo orientation objective at all
Track a specific normal force setpointNo force setpoint. Force is bounded and logged, not tracked
Hold still for 3 seconds (a "dwell")No dwell. A short settling check instead
Spot inspection at one pointTrace a trajectory across the wall while in contact

What survived unchanged is the thing the research question needs: the two-channel correction interface d = (F̂ₙ, τ̂_pitch) described in Section 11.

So the current task in one sentence: the drone holds a fixed position in the air while its arm's own end effector draws a path on a wall, staying in contact the whole time. The drone must not drift, even though the arm is moving and the wall is pushing back.

Section 4The robot

Everything runs in MuJoCo, a physics simulator. There is no hardware. The design lives in one file — Code/config/am3_design_v3.json — and the simulation model is generated from it by Code/scripts/am3_build_model.py, so geometry and inertia can never drift apart.

Honesty about parameters

The rotor numbers are a declared simulation assumption, not measured hardware data — there is no published thrust table for this vehicle. The servo continuous torque (1/3 of stall) is also an assumption. Both are labelled as such in the config file, and a ±20% sensitivity sweep is part of the mismatch suite. This matters: a reader should never mistake simulation self-consistency for hardware fidelity.

Why the contact patch is small

The usable wall patch is only ±5 cm wide. The reason is yaw authority. When the pad presses the wall at a lateral offset y, the friction force acts at the end of a 0.28 m lever, producing a yaw moment on the vehicle. A quadrotor can only generate yaw torque through rotor drag, whose arm here is just 0.016 m — roughly 17× weaker. Push too far off-centre and a rotor would need negative thrust, which is impossible. So the geometry of the task is set by the weakest axis of the vehicle, not by arm reach.

Section 5Why coupling is the entire problem

Write the whole system — vehicle and arm — as one rigid-body chain with generalised velocity

ν = (v, ω, q̇) ∈ ℝ⁹ — base linear (3), base angular (3), joint rates (3)

The equations of motion are

M(R,q) ν̇ + b(ν) + G = τ_rotors + Sᵀτ_joints + J_cᵀ f_contact

M is the 9×9 mass matrix. Split it into blocks:

M = ⎡ M_bb M_bq ⎤ M_bb : 6×6, how the base resists acceleration ⎣ M_qb M_qq ⎦ M_qq : 3×3, how the joints resist acceleration M_bq : the 6×3 cross block — the coupling

M_bq is the whole argument. It says that accelerating a joint applies a force and a moment to the airframe, and vice versa. A decoupled controller sets M_bq = 0: it models the drone as a rigid body of the right total mass, and the arm as a separate manipulator, and assumes neither notices the other.

Is M_bq actually big enough to matter? We measured it. Over 50 random states, the smallest value of its largest entry was 0.033 — never anywhere near zero. (Code/scripts/am3_check_pred.py, output in Code/results/am3_predictor/static_checks.json.)

There are three physically distinct effects hiding in that block:

  1. Inertial reaction. Swinging the arm pushes the airframe the other way — conservation of momentum.
  2. Centre-of-mass shift. The system COM is not at the base origin and moves as the arm moves. Thrust is applied at the rotor plane, so it produces a moment about the true COM that changes with arm configuration.
  3. Coriolis / gyroscopic terms. Base rotation and joint motion interact through the velocity bias b(ν).
Experimental proof

Section 14 describes a test where the drone is asked to do nothing — just hover — while the arm moves. The coupled controller holds position to 0.127 mm. The decoupled controller tips over to 40° and is cut off by the safety monitor after 13.6 seconds. No trajectory, no contact, no disturbance: that failure is purely M_bq.

Section 6Two models, deliberately kept apart

This is the single most important architectural decision in the codebase, and it is easy to miss.

The plantThe predictor
Fileocrl/am3_plant.pyocrl/am3_pred.py
What it isMuJoCo — the "real world"CasADi symbolic model — what the controller believes
Built fromthe generated MuJoCo XMLonly am3_design_v3.json
Roleground truth for every controllerthe model inside the NMPC

The predictor never queries MuJoCo. It re-derives the kinematics, the 9×9 mass matrix, the gravity and velocity bias, the rotor model and the contact law from scratch, symbolically, from the design numbers.

Why do the work twice?

If the controller's model were extracted from the simulator, then "the model matches the plant" would be a tautology and would prove nothing. Because the two are independent derivations, agreement between them is evidence. And it does agree: forward kinematics to 3.3×10⁻¹⁶, Jacobians to 2.8×10⁻¹⁶, the full mass matrix to 1.0×10⁻⁹, accelerations to 5.4×10⁻⁶.

It also buys the thing the research question needs: because the predictor is a separate object, you can deliberately make it wrong — different payload, different contact stiffness — and study what the controller does about it. That is the entire mismatch experiment.

The predictor is also the ablation mechanism. Passing coupling="decoupled" replaces M with its block diagonal and zeroes the cross terms in the bias — producing controller Nd, which is identical to N in every other respect. That isolates the modelling choice from everything else.

The harness is where fairness is enforced

ocrl/am3_episode.py runs the closed loop. Every controller gets, identically:

  • the same noisy measurements (0.1 mm position, 0.01° attitude, 1 mm/s velocity, 10 mN force);
  • a one-period computation latency — the command computed now is applied next period, as on real hardware;
  • the same task logic and contact policy;
  • the same safety monitor (abort at 40° tilt or 250 mm position error).

A controller is just an object with compute(t, xm, Fm, task) → (u, info). Because there is exactly one place where unfairness could enter and it is shared, the B-vs-N comparison is structurally honest rather than honest-by-inspection.

Section 8Controller N — the coupled NMPC

What it optimises

At every control step (50 Hz) it solves a constrained optimisation over the next 10 steps of 20 ms — a 0.2 s look-ahead:

minimise Σⱼ ‖r(xⱼ, uⱼ)‖² + ρ‖s‖² + ρ‖s‖₁ subject to x_{j+1} = Φ(xⱼ, uⱼ) RK4, 4 substeps x₀ = current estimate rotor and torque bounds hard tilt, joint, force limits soft, with slack s

State and input

23 states: position (3), quaternion (4), world velocity (3), body angular rate (3), joint angles (3), joint rates (3), rotor speeds (4). Inputs: 4 commanded rotor speeds + 3 joint torques.

Why rotor speeds are states

Motors cannot change speed instantly — 40 ms spin-up here, which is two whole control periods. If thrust were treated as directly commandable, the controller would plan manoeuvres the motors physically cannot deliver. Carrying rotor speed as a state with a first-order lag means the optimiser knows it must ask early.

The cost terms

All residuals are normalised by a physical tolerance, so the weights are dimensionless and comparable:

  • pad position vs reference (σ = 1–2 mm) and pad velocity
  • base position vs its fixed reference (σ = 5 mm) and base velocity
  • small regularisation on attitude, angular rate, joint rate
  • input variation — penalises jerky commands

Notice what is absent: no orientation target, no force setpoint, no alignment term. Those were deleted with the scope change.

Constraints

Hard: individual rotor speed bounds, joint torque bounds. Soft (with named, normalised slack variables): 15° tilt, operational joint ranges, joint rate, 4 N contact force cap, closing speed during approach, clearance of elbow and wrist below the rotor plane.

Why soft constraints

A hard constraint that becomes infeasible makes the solver fail, and a failed solver on a flying vehicle is a crash. Softening with a heavily penalised slack means the optimiser will violate a limit slightly rather than give up — and because every slack is named and logged, any violation is visible afterwards. Soft constraints are not guarantees, and the code says so.

Two solvers, one formulation

am3_nmpc.py builds the residuals, constraints and dynamics once, then hands the same expressions to IPOPT (a reliable reference solver) and to acados (a fast embedded solver using SQP real-time iteration). Cost and constraint parity is therefore true by construction, not by hand-matching two implementations. They were checked to agree to 1×10⁻⁹ relative cost and 1×10⁻⁴ on the first input.

Why acados, and what RTI means

IPOPT solves the problem properly but takes far too long for a 20 ms budget. acados in SQP-RTI mode performs one Newton-type iteration per control step, reusing the previous solution as a warm start. It is not converged optimisation — and the code is careful never to claim it is. It is the standard trade for real-time nonlinear MPC.

Delay compensation

Because the command will not take effect until next period, the controller first propagates the measured state forward one period using the command already in flight, then solves from that predicted state. Without this the controller is always one step behind, which at 50 Hz is enough to destabilise contact.

Section 9Controller B — the baseline that must not be a straw man

The whole comparison is worthless if B is weak. Plan.md is explicit: "Do not make the baseline fail on purpose." So B gets every reasonable advantage:

  • a geometric (SE(3)) hover controller — the standard, well-respected quadrotor method;
  • the correct total mass 1.52 kg and gravity compensation;
  • a declared nominal inertia about the locked-posture COM;
  • moment trim initialised from rotor telemetry;
  • latency compensation and partial inversion of motor lag;
  • joint-space arm control with feedforward from the arm's own model;
  • the contact force implied by the shared policy, fed forward;
  • 200 Hz — four times N's rate;
  • a tuning budget at least as large as N's: linearised scans, 56 grid points, 320 random-search samples.

The only structural thing it lacks is M_bq — it does not model that the arm pushes back on the base.

Why 200 Hz, and the caveat it creates

B was first tried at 50 Hz to match N. It was unstable for every gain set tested — a light arm under torque control with 40 ms of effective delay simply cannot be stabilised that slowly, and the linearised closed-loop spectral radius exceeded 1. So B runs at its natural rate. This is the fair choice, but it means the B-vs-N difference bundles three things: model, architecture and rate. That is why the NMPC ablation Nd exists — Nd differs from N in the model alone.

Section 10The task machine and contact policy

ocrl/am3_task.py sequences every run and is shared by all controllers:

hover → position → approach → settle → trace → endhold → release → retreat → done ↑ ↓ └──── recover ←────┘ on confirmed contact loss

Crucially, this module never reads the simulator. It only sees the measured normal force and a measured gap — the same information a real system would have.

Detecting contact

Contact is declared with hysteresis: force above 0.15 N for 3 consecutive samples turns it on; below 0.08 N for 5 samples turns it off. Two thresholds instead of one prevents chattering at the boundary.

Pressing without a force setpoint

Since the task has no force target, the controller commands a small indentation instead — it asks the pad to be 1 mm inside the wall surface. With a 600 N/m contact stiffness that produces about 0.6 N of preload. The approach creeps in at 2 cm/s, slowing to 1 cm/s near the surface, and continues past zero gap until contact is actually measured.

Why indentation and not force

You cannot simultaneously demand zero gap and a specific force against a compliant surface — those are two conflicting statements about the same contact. Commanding a small penetration against a known stiffness is self-consistent, and it degrades gracefully: if the surface is stiffer than modelled you get more force, not a controller fighting itself.

Recovery

If contact is lost mid-trace, path progress pauses (it does not keep running in the air), the controller re-approaches, re-settles, and resumes. The lost time is counted and reported. Recovery cannot erase impact peaks or let an incomplete path pass as complete.

Section 11D and L — where the research question lives

This is the part the proposal was really about, and it is unfinished.

The idea: let something learn a correction to the NMPC's model, not to its output. The correction is deliberately tiny — two numbers:

d = (F̂ₙ, τ̂_pitch) normal-force channel, pitch-moment channel τ_d = D(x) · d injected into the prediction dynamics
Why correct the model instead of the action

The best-known approach (residual RL) adds a learned term to the controller's output. That works, but the learned part bypasses the optimiser entirely — it can violate thrust limits, tilt limits and contact bounds, because nothing checks it.

Here the correction goes into the prediction model, before optimisation. The NMPC still produces the final command, so all constraint handling and feasibility reasoning stay intact. The learner can only change what the controller believes, never what it is allowed to do. This is the project's main methodological contribution, and the taxonomy table in Findings/Research/literature_matrix.md records that no prior work was found doing exactly this.

Three controllers share this one interface (ocrl/am3_ctrl_corr.py), with identical magnitude and rate limits:

  • Z — zero correction. Must reproduce N exactly; this is the parity test that proves the interface adds nothing by itself.
  • D — classical. An augmented error-state EKF estimates the two channels from the residual between predicted and measured behaviour.
  • L — learned. A SAC policy outputs the two channels from measured state, contact signal, path progress, previous commands and a short force-residual history. Its reward covers hover error, path tracking, contact loss, excessive force and correction effort. It gets no privileged information — no true mismatch parameters, nothing D cannot also see.
Current status — and an honest caveat

On the 20-scenario mismatch development list: N scores 11/20, D scores 13/20. A modest win for the classical method. L has never been evaluated — its training was paused at roughly 100k of 200k steps, and the checkpoints are not in this repository.

There is also a known structural limitation: tangential friction and general payload error do not necessarily lie within the span of two channels. The plan requires quantifying that projection error rather than letting an unrepresentable disturbance be mistaken for a failure of learning.

Section 12How we prove things — the part that makes the results trustworthy

CLAUDE.md sets rules that the codebase genuinely follows. They are worth understanding, because they are why the numbers can be believed.

Simulation is the proof, not the metric

A controller is not "done" because its numbers look good. It must be seen working in a reproducible run with a real recording. Every result directory contains the command, the config hashes, the seeds, raw logs and video.

Freeze before you test

Before the held-out evaluation, Code/scripts/am3_freeze.py records a SHA-256 of all 22 files that define the controllers and the task, plus library versions. The pass thresholds were written before any held-out run and derived from the task — not from observed performance:

CriterionThresholdWhere it comes from
base position error≤ 20 mm1/15 of arm reach
pad tracking RMS≤ 3 mmquarter of pad radius
endpoint error≤ 5 mmtask tolerance
path coverage within 5 mm≥ 95%task completeness
contact-valid fraction≥ 95%inspection validity
peak normal force≤ 4 Npad compression limit
tilt≤ 15°the NMPC's own constraint

This ordering is what makes the gate meaningful. Thresholds chosen after seeing results are not thresholds, they are decoration.

Three separate scenario sets

Development (for tuning), validation (for checkpoint choice), held-out (used once). N was tuned on development scenarios with exactly one validation observation, recorded in the findings. Held-out data were not used for tuning.

Equivalence evidence when a frozen file changes

Frozen files cannot be edited casually. When the flight demos in Section 14 required four of them to change, each change was additive and defaulted to the previous behaviour — and that was proven by re-running the benchmark and comparing logs element by element. Result: maximum absolute difference exactly 0.0 across states, commands, forces and pad positions. Nothing previously validated was disturbed.

Report failures at equal volume

The media log documents failed experiments with the same detail as successes, including a baseline gain set that diverged on 5 of 16 scenarios and nine unsuccessful attempts to stabilise the Nd ablation. When a run aborts, its video panel freezes on the last frame under a red banner stating the time and cause — never looped, never cropped out.

Read these three rows together, because they say different things. Independently reproduced

On 27 Oct 2026 these results were rebuilt from scratch on a different machine — fresh environment, freshly compiled solver. Baseline B reproduced bit-for-bit. N reproduced to within a few percent (base RMS 0.178 → 0.174 mm), the difference being that the solver's generated C is compiled with -march=native, so floating-point results differ in the last bits and feedback amplifies them.

The real-time problem — the most important caveat

N is not real-time compliant as built

The control period is 20 ms. On a quiet machine N's median cycle is 15 ms, but 1.3–1.7% of cycles exceed 20 ms, in a burst during the final approach to the wall. When deadlines are strictly enforced (a late result is discarded), N loses control at about 5.4 s.

Measured on a faster machine the picture improves markedly — median 9.3 ms, 1.3% over deadline — which shows the limitation is hardware-dependent. Remedies exist but are untried: bounding QP iterations, fewer integration substeps or horizon stages, and an OpenMP build (the current build reports "acados was compiled without OpenMP").

Never compare timing numbers across machines without naming the machine.

Under model mismatch

On the 20-scenario development list with deliberately wrong payload, contact stiffness, friction or propulsion: N 11/20, D 13/20. Nominal accuracy is an upper bound — with a predictor that matches the plant by construction, N is at the sensor-noise floor, and that flatters it.

Section 14The flight demonstrations (added 27 Oct)

Plan.md pins the drone to a fixed hover point, because the inspection task is "hold still and move the arm". To show the controller flying, four things were added. All default to the old behaviour, all verified bit-exact (Section 12).

  1. A moving base reference. The NMPC already carried the base reference as a per-stage parameter. What was missing was a base velocity reference — velocity was being driven to zero, which fights a moving target and causes lag of roughly 83 ms × speed.
  2. An analytic periodic task (ocrl/am3_traj.py). The base follows a Lissajous figure y = A sin(n_y θ), z = C sin(n_z θ + φ); the arm circles the moving base. One smoothstep envelope ramps the rate 0 → 1 → 0 so motion starts and ends at rest while completing exactly the requested number of laps.
  3. Free-flight options — remove the wall from collision and rendering, start with the arm hanging down.
  4. A reference-relative failsafe — see the bug below.
A real bug found this way

The shared safety monitor measured position error against the fixed hover point. A drone legitimately flying a 345 mm figure-eight therefore tripped the 250 mm abort while perfectly on reference — both controllers reported "loss of control" at 3.7 s with 0–1° of tilt and 0.139 mm of tracking error. Without checking, this would have been reported as "the large trajectory fails". It now measures against the current reference. The same bug would have affected the planned long-line wall test.

What these runs show

All 30 s, each pair on the same plant, reference, seed and sensor noise:

In free flight B does not merely track worse than on the wall task — it diverges every time, and fastest when the arm simply hangs. A 0.47 kg arm suspended 400 mm below the airframe is a harsher reaction load than the tucked contact posture B was tuned for.

Two caveats to state before anyone asks

It is a modelling failure, not saturation. When B loses control, N is using about half the thrust envelope and a fifth of the joint-rate limit. The control authority is there; B does not know the arm pushes back.

B was never retuned for free flight. Its gains were searched for the fixed-hover wall task. The defensible claim is "B as tuned for the original task diverges here", never "no decoupled controller could do this". These demos also sit outside the frozen plan and are not covered by the 30-case gate — they are capability demonstrations, not validated evidence.

Section 15What is unfinished

Checklist state from TODO.md: items 3, 4, 5, 7, 8 partial; item 9 open.

The research question is not answered yet

  • L has never been evaluated. SAC training paused at ~100k of 200k steps; checkpoints absent from the repository. Until L runs, the headline question has no answer.
  • The N/D/L comparison exists only on a 20-scenario development list. No frozen, paired, held-out comparison has been run.
  • Generalisation outside the training range — a stated goal — is untested.

Known gaps in validation

  • Predictor contact validation covers approach and impact, but sliding, reversal and contact loss remain open.
  • N is not real-time compliant; the listed remedies are untried.
  • N's weights were set from a first guess and never tuned — acceptable only because N is at the sensor-noise floor nominally, and not necessarily acceptable under mismatch.
  • A stable decoupled NMPC (Nd) may exist outside the nine weight sets searched.

Requested demos not yet built

  • A long line on the wall — needs the moving base, since the patch is capped at ±5 cm by yaw authority.
  • Writing letters on the wall — multi-stroke with pen-up/pen-down sequencing.
  • A curved surface (a ball). This one is substantial, not a configuration change: the gap and contact normal are hard-coded to a plane with n = (−1,0,0) in both the MuJoCo model and the CasADi predictor. A sphere needs a state-dependent normal and full re-validation of contact onset, sliding and impact.

Section 16Running it

The repository does not run out of the box: the solver, the RL checkpoints and the raw logs are excluded from version control. Full setup is in SESSION_CONTEXT.md. Once built:

cd Code
export ACADOS_SOURCE_DIR=$PWD/third_party/acados
export LD_LIBRARY_PATH=$ACADOS_SOURCE_DIR/lib
P=/path/to/venv/bin/python

$P scripts/am3_check_pred.py              # predictor vs MuJoCo — start here
$P scripts/am3_run.py demo N line         # one closed-loop run
$P scripts/am3_compare.py TAG line        # matched B/N run with video
$P scripts/am3_live.py N line             # interactive viewer, watch it live
$P scripts/am3_batch.py GATE heldout N --workers 8 && $P scripts/am3_gate.py GATE config/am3_acceptance_v1.json
Two traps

A second, different acados build may exist elsewhere on the machine and the shell's default environment variables may point at it — always override them. And batch timing measured with parallel workers is invalid; the repository's own notes flag this about an earlier run.

Section 17Glossary

NMPC
Nonlinear Model Predictive Control. Repeatedly solve a short-horizon optimisation using a nonlinear model; apply the first command; repeat.
SQP-RTI
Sequential Quadratic Programming, Real-Time Iteration. One Newton-type step per control period instead of solving to convergence.
acados / CasADi
CasADi builds the symbolic model and derivatives; acados generates and runs fast C solver code from it.
M_bq
The cross block of the mass matrix coupling base and joint accelerations. The thing this project is about.
Plant / predictor
Ground-truth simulation vs the controller's internal model. Kept independent on purpose.
N / B / Nd / D / L
Coupled NMPC / decoupled baseline / NMPC with decoupled model / EKF-corrected / learning-corrected.
Gate
A held-out evaluation against criteria frozen before the run.
Mismatch
A deliberate difference between plant and predictor — wrong payload, stiffness, friction, thrust.
Slack
A penalised variable letting a soft constraint be violated slightly rather than making the problem infeasible.
