# Controllers for design v3 (25 Oct 2026 plan)

All controllers act on the same MuJoCo plant (`Code/ocrl/am3_plant.py`, design v3, coupling never removed), receive the same noisy state and force measurements (`am3_episode.Sensors`: 0.1 mm / 0.01 deg / 1 mm/s estimator-grade state noise, 10 mN force noise), use the same task logic and contact policy (`am3_task.py`) and the same actuator limits (rotor speeds 180..1800 rad/s with lag 40/60 ms, servo envelope 1 N m continuous / 3 N m stall). Commands pass through a one-control-period computation latency.

## Baseline B versions kept (v1-v3 discarded 30 Oct 2026)
| | B v4 (`am3_ctrl_b_v4.py`, `make_ctrl("B4")`, gains `am3_b_gains_v4.json`) | B v5 (`am3_ctrl_b.py`, `make_ctrl("B")`, gains `am3_b_gains_v5.json`) |
|---|---|---|
| Architecture | one controller object; arm and drone parts share information | `DroneController` and `ArmController`, nothing exchanged |
| Contact force | wall force implied by the indentation reference fed forward into drone thrust and arm torques | only the arm feeds forward its own intended contact force; drone has none |
| Pad feedback | slow measured-pad correction (k_corr) into the arm reference; arm IK uses the drone pose | none; fixed mounting assumption |
| Task gap | measured from the drone pose | the task's own gap reference |
| Gate v2 held-out (30 scenarios) | 0/30; base max median 33.3 mm | 0/30 (GATE_v3_B); base max median 29.8 mm |
| Line recording, trace RMS / mean Fn / contact fraction | 13.2 mm / 0.54 N / 1.00 | 17.7 mm / 0.17 N / 0.78 |
Older B versions v1-v3 (grids, random search, the hover-unstable v3) were deleted at the user's request; the tuning stages that produced v4 (`stability_search.json`, `stage5/6`) remain as provenance. Use v5 for the B-versus-N comparison requested on 30 Oct (separate controllers); v4 only to reproduce earlier results.

## Baseline B v5 (`am3_ctrl_b.py`, gains `config/am3_b_gains_v5.json`): two strictly separate controllers
`DroneController` and `ArmController` exchange nothing at run time (30 Oct 2026, user request). The plant stays fully coupled; only the information boundary is cut. The previous information-sharing B (v4) is archived as `am3_ctrl_b_v4.py` (`make_ctrl("B4")`) and its gate-v2 / 30 Oct v4 recordings stay reproducible.
* **DroneController** input: drone position, attitude, velocity, angular velocity, rotor speeds; fixed reference BASE; output: four rotor-speed commands. Fixed design constants: total mass, nominal locked-posture COM and inertia (0.0089 / 0.0167 / 0.0114 kg m^2), hover-trim moment initialised once from rotor telemetry at t0. Geometric position PID + SO(3) attitude PD+I, kinematic prediction over the command latency, 4x4 allocation. **No** arm joint state, arm/task reference or phase, wall-force measurement, indentation-derived force feedforward, or configuration-dependent COM/inertia.
* **ArmController** input: joint angles and rates, and its own reference (pad position, velocity, acceleration, gap-implied contact reference from the task); output: three joint torques. IK + joint PD + feedforward of the arm's own (decoupled) model, plus the contact-force torque J^T F for the wall force implied by its own indentation reference. **No** drone state, rotor command or drone-controller output. Documented mounting assumption: the drone sits at BASE with pitch atan(F_ref / m g) derived only from the arm's own contact reference (0 in free flight). **Reference generation does not use the measured base pose**; there is no pad-position feedback (the old k_corr loop is removed).
* **Shared infrastructure**: both read the same noisy sensor object, which is deterministic in (seed, time) and carries no controller state. The shared task state machine is advanced with the arm's contact-force measurement and, for B, its own gap reference (`task_uses_state = False` in `Episode`) instead of a gap computed from the drone pose, so no drone information reaches the arm through the task. The drone side never sees the task.
* **Verification**: `Code/scripts/am3_check_b_separation.py` (static signature/identifier check; bit-exact invariance of rotor commands to arm states, task reference and contact force over 300 steps; bit-exact invariance of joint torques to drone states and rotor speeds; spy on the task gap passed by `Episode`).
* **Removed information paths vs v4**: (1) wall-force/indentation feedforward into the drone thrust; (2) task/contact phase and pad reference into the drone controller; (3) measured pad position (hence drone pose) into the arm via the integral correction loop and pad FK; (4) drone-derived measured gap into the shared task for B; (5) drone state into the arm's IK base pose (the arm now uses the fixed mounting assumption).
* Rate and delay unchanged: **200 Hz, one-period (5 ms) latency**; N 50 Hz, 20 ms latency, 0.2 s preview. Gains are the v4 numbers (no retuning), `k_corr` dropped. The B/N difference therefore includes rate, latency, preview, architecture and model; it is a practical comparison, not an isolation of one coupling term.
* Omitted by construction: arm-base inertial cross blocks (M_bq), reaction of arm motion on the base, COM shift, joint optimisation. With free joints the effective pitch inertia about the COM is 0.0027 kg m^2 (`Findings/Physics/`), 6x below the locked-posture value assumed.
* **Tuning history** (unchanged from v4): B v3 was unstable in stationary hover (audit B01); stages 5-6 produced the v4 gains (`stability_search.json`, `stage5.json`, `stage6.json`). The separated B v5 was **not retuned**; its 30 s stationary hover at four postures with and without kick is stable (`results/am3_physics/hover_check_B.json`, base 0.2-0.4 mm in the last 10 s).
* Not done for B: explicit bounds/singularity checks on the 8-step Newton IK (audit B10).

## Coupled NMPC N (`am3_nmpc.py`, `am3_ctrl_n.py`)
* 23-state predictor with the full 9x9 mass matrix, gravity and velocity bias, rotor lag, spherical-pad wall contact with regularised Coulomb friction, built only from the design config (not from MuJoCo); one CasADi formulation drives IPOPT (reference) and acados SQP-RTI (production). N=10 stages of 20 ms, RK4 with 4 substeps.
* Cost (normalised least squares): base position/velocity about the **fixed** hover reference, pad position and velocity along the task reference, small attitude/rate/joint-rate terms, input variation. No orientation reference, no force setpoint, no alignment term, no terminal LQR (terminal = running residual).
* Soft constraints with named normalised slacks: tilt 15 deg, operational joint ranges, joint rate, normal force <= 4 N, closing speed during approach, elbow/wrist height below the rotor plane; hard rotor-speed and joint-torque bounds.
* The measured state is propagated one period with the pending command before solving. Failures retry once from a reset, then fall back to the previous command (logged).
* **Model ablation Nd**: identical costs, constraints, solver settings, only the predictor uses block-diagonal M and per-block bias (gravity kept). In development runs Nd diverged ~0.4 s after the arm started to move (abort logged in `Code/results/am3_runs/dev_Nd_*`).
* IPOPT/acados parity at four task states: cost agreement 1e-9 relative, first input within 1e-4 rad/s (`Code/results/am3_predictor/solver_parity.json`).

## Known limits
N's stage weights were set from a first guess, then tuned on development scenarios (`results/am3_n_tuning/`: 8 weight sets on fast paths) and the wall-normal pad weight was doubled after one contact loss in a validation scenario (so that validation list is no longer untouched); held-out lists were not used. N is at the sensor-noise floor in nominal runs. All nominal runs use a predictor that matches the plant by construction up to integration and contact calibration; mismatch robustness is not yet evaluated (D/L comparison).
